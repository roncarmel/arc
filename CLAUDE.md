# Arc

Arc (was Ceremony Playlist Builder; renamed by Ron, 2026-11-08), "Ceremony playlist tools for your Spotify library": two tools on one home page, the **Playlist builder** and **Music sharing**. A free, browser-only web app (arc.roncarmel.com, was playlists.roncarmel.com until 2026-11-08; GitHub Pages, no server) that builds long timed Spotify playlists for ceremony and retreat sessions from the person's own playlists. The owner is Ron, who uses it with clients. It is not public yet, so file formats and wording can still change freely.

## How it works

- Each person makes their own Spotify app (a free Client ID, development mode) and pastes the Client ID in. Sign-in is Spotify's PKCE flow in the browser: no secret, no backend.
- A **recipe** says which of the person's playlists to draw from, in what order, for how many minutes, with silence between segments. The app builds one playlist from a recipe for a participant, songs they have not heard first.
- Pyodide runs `engine.py` in the page (songs are picked there). Everything else is plain JavaScript in classic `<script>` files (no build step, no modules, shared global scope).
- Anything the person types goes nowhere but their browser and their own Spotify account. Do not add servers, trackers, or anything that sends their data elsewhere (the only third parties are Spotify, the Pyodide CDN, Arc's media worker for the tutorial video, a GoatCounter page-view counter, a Tally form only in the startup problem popup (its address carries scrubbed details; the page's own form needs scripts that may have failed), and Deezer for song previews in Music sharing, sent only a song's ISRC when its play button is pressed). The exceptions are the wait relay (see "Spotify's limits" below) and Music sharing's worker (see "Music sharing" below), which also emails Report a problem and Feedback to Ron (see Interface).

## Decisions worth knowing (and why)

- **Free, a community service** (decided by Ron, 2026-11-08): no subscription, trial, paywall or support requests. Support me (Ko-fi button, panel, the thank-you box with Ron's photo after a build, Hide support button) was removed the same day; it is in the git history before version 2026-11-08zr. Arc earns goodwill, not money.

**Saving recipes**
- **Saving is on closing the panel** (decided by Ron, 2026-11-12, replacing autosave; Done in place of the X since 2026-11-13): every edit still goes to `localStorage` at once, but a recipe open in the recipe panel goes to Spotify only when the panel closes: Done, Escape or a tap outside all save. There is no Cancel or Discard (a mistake is changed back by hand; a new recipe closed as it was made is dropped, not saved: `recipeEdit.blank`, Ron, 2026-11-14). While it has changes, `recipeEditing` in localStorage holds `{id, before, dirty}` (`recipeEdit`, `recipeEdited` called from `commit()`, in editor.js), and the cloud save and the merge leave that recipe alone (`heldRecipeId` in app.js), so a closed tab keeps them and the landing shows Unsaved changes. Changes count by `contentSignature`, so undoing them is no change.
- Recipes live in `localStorage` (`formats`) and are saved there on every edit. They are always also **saved to Spotify**: one private playlist per recipe named `<title> (recipe)`, the recipe packed into its description ("Holds a recipe, not music. Do not edit." plus dense CJK characters; saves with only "Do not edit." are still read, 14 bits each, magic "CP", version, CRC-16; `SAVE_LIMIT` is 300 characters because Spotify's own app shows 300; the API accepts 512). Saves are found by decoding descriptions, not by name.
- Backup by hand (a download and restore, `backupMode` "manual") and its Autosave or backup choice were removed by Ron, 2026-11-14: Change Spotify login copies this browser's recipes into another account, and nothing else Arc keeps in Spotify needs a file. A browser that had chosen it now saves to Spotify; `backupMode` is no longer read. Only the tests turn saving off (`savingToSpotify`, `arcTestNoSaves` set by `boot`).
- Every recipe has a `revision` and `modified`, written only after its first edit. `mergeFromSpotify` (app.js) settles each recipe against its save using a per-device record `spotifySynced` (`{id: {rev, playlistId}}`): only one side changed means that side wins; both changed, or no record and a difference, opens a **required** dialog (no Escape, no backdrop close). A save that is gone from Spotify asks too (keep or remove). Each time the merge asks, what it saw (the recipe, its `spotifySynced` record, whether that playlist was in the list, the saves listed, when and by which code the list was read: `playlistsLoadedBy`, `callerTrail`) is kept, the last 10, in `syncAsks` (`recordSyncAsk`), included in Copy Spotify request log, and in developer mode behind Copy details on the question (`debugLink`); Ron saw the gone-save question with the save still there (2026-11-12), and a re-check of the playlist before asking was held back until the cause is known. Ron then found 7 saves of each recipe (2026-11-12): each time a save makes a new playlist, what it saw is kept too, the last 20, in `saveCreates` (`recordSaveCreate`), with Spotify's own total for the list (`playlistsTotal`), whether the list was read again during the save, and the recorded save playlist read on its own with whether it is in the library (`readSaveDirectly`, also on each gone-save question). Every list read also records, once per set, two or more saves of one recipe (`saveDuplicates`, `recordSaveDuplicates`), with each one's place in the list and the list's pages as Spotify sent them (`playlistPages`). Every list read is kept too, the last 30 (`listReads`, `recordListRead`: count against Spotify's total, the saves it showed), and every record names its tab (`TAB_ID`), since tabs of one browser share them: the log showed two bursts of new saves with no list read between, which one tab cannot do. The bursts of copies on 2026-11-12 came minutes after pushes, so each record also has the page's state (`pageState`: script versions, `updating`, `startupRefreshed`, time since the page started). Cause found 2026-11-13: Spotify sent the list's first page empty (0 of 98, with more to come), so both saves looked gone. A page that comes back shorter than its total says is read again, up to 3 times (`loadMyPlaylists`; in developer mode a short page that came right says so on the line under the bar). A list still short is never used (Ron, 2026-11-13: no half-known state): `loadMyPlaylists` throws `SHORT_LIST_MESSAGE`, Arc counts as not connected and waits like a rate limit (`startLimitWait("short")`, `limitWait.reason`): a popup once a wait (`showShortListDialog`: Spotify didn't send all your playlists, This happens now and then. Arc will keep trying. Until then you can edit your recipes, and building waits., OK and Report this problem), the strip Waiting for all your playlists · M:SS (Details reopens the popup), Build buttons greyed (`bh-waiting`), the playlists already known or the kept list for the menus, and tries again after 30 s, 2 min, 10 min, then every 10 min (`SHORT_LIST_RETRY_MS`); when all of it arrives, All your playlists arrived. on the line under the bar, and saves and deletes that waited go. Each short list is recorded as an error with its counts. Spotify's forum has years of reports of `/me/playlists` sending short, empty or duplicated pages, with no fix from Spotify. A `null` item (a playlist Spotify will not show an app in development mode, such as its own, though its total counts it) counts as arrived and is left out of the list; how many and where are in the record (`playlistsHidden`, `hidden` in `listReads`). Spotify more often leaves such playlists out of its pages altogether: a page short the same way twice (the same playlists in any order, not empty) is taken as all there is (`steady`, `leftOut` in `listReads`), and reads of a page that differ are joined, whole when together they reach its count (`joined from reads`). Reading short pages again stops after 10 s in all (`LIST_RETRY_MS`). A build does not read the list again when it was read in the last 3 minutes (`BUILD_LIST_FRESH_MS`), and a list read again for a build (and after it) that comes short leaves it on the whole list already held, with no wait (`loadMyPlaylists({ keepIfShort })`); it shows Reading your playlists · 7 of 19 for a list of more than 3 pages (`onPage`). Ron, 2026-11-15: her build sat a minute on Reading your playlists and then failed; the never-half-known rule stays for connecting, saving and merging. A list still short records its counts and each short read (`[offset, items]`) as the error a report carries, and `recordError` keeps it over the bare message caught further up (a failed build replaced it, 2026-11-15). Without that, an account following 4 of them never connected (937 of 941, then 939 of 943, the first user report, 2026-11-15). Recipes found only in Spotify are added. Deleting a recipe deletes its save (`spotifyPendingDeletes` survives a closed tab). Unreadable saves are rewritten in place if they have the recipe's name, and never deleted.
- Before a save, the account's playlists are read again unless read in the last 5 s (`SAVE_FRESH_MS`) or the page is being hidden, so with Arc open on two devices the second save asks instead of writing over the first (found by Device checks, 2026-11-14).
- Saves are debounced 5 s with a 30 s maximum wait, flushed when the page is hidden, retried when the connection returns, paused while a build runs. A second failure in a row, or an unexpected one, opens a popup (try again / close / report).
- **Covers** (`recipe-cover.jpg`) are queued and sent after a save is done, one at a time, never waited for: a rate-limited upload stops the rest quietly and they go with a later save (`uploadCovers`, `noWait` on `spotifyRequest`). A save rewritten from the old "Do not edit." note gets the new cover once even though it has one (`recipeCoverDue` in localStorage until sent). When the cover changes, `RECIPE_COVER_LOOK` (app.js) changes with it, and each browser that has not sent that look (`recipeCoverLook`) sends it once to every save that has a cover.
- Wording rule: say nothing about where the recipes are kept, like a Google Doc ("Saved to Spotify"). The exceptions are the Privacy section, and Sign out and clear data (was Reset app on this device; renamed by Ron, 2026-11-05, for its real use: leaving a computer that isn't yours, or a last resort), which must say what they erase. It copies nothing to the clipboard (at odds with its use); `startOver()` does the same and copies the Client ID first (the DEV menu's Clear data and start over).

**Spotify's limits**
- Spotify does not publish its limits, and a page cannot read Retry-After (Spotify's CORS does not expose it). So the app keeps its own record in localStorage: requests per minute by kind (`spotifyCalls`, 8 days) and each refusal with the requests before it, the last refusal and when it cleared (`spotifyLimits`).
- Songs are added 100 per request (Spotify's documented maximum; it was 10). If Spotify answers 400, the rest of the visit uses 10 and the record notes it.
- After a rate limit with no readable wait, every user's page automatically asks the wait relay (`WAIT_RELAY_URL`, `askSpotifyWait`): one GET /me through Ron's worker, shared by requests refused together and reused for 30 s. Its wait goes into the usual message and the record. Not for cover uploads (their own limit). Disclosed in one Privacy paragraph (`privacyWaitRelay`); decided by Ron, 2026-11-02, as automatic for everyone.
- A wait of over a minute (not for covers) is kept in localStorage (`spotifyPausedUntil`: until, when it began, reason, Client ID) and nothing goes to Spotify until it ends (`spotifyPause`, `tickPause`). A strip under Arc's bar on every view (above home's band, in home's column) shows a clock, "Spotify asked Arc to wait · H:MM:SS" and Details, and opens the popup (`#waitStrip`, `paintWaitStrip` in app.js; Music sharing's page starts under it; it replaced the pink line under the editor's bar); the Build button is hidden; the popup (`showPauseDialog` in editor.js: a ring with the countdown and end time that empties as the wait passes, one list of what works and what waits, why) opens by itself only when a wait starts. Decided by Ron, 2026-11-02, over a blurred screen.

## Tests

See `tests/README.md`. The whole suite is `tests/run-all.sh` (each area in its own Node process, `EXACT_AREA=1`, prints only failures and the totals; Ron, 2026-11-15), never `node run.js` alone: one process for everything held dozens of copies of Arc and ran out of memory, and the VM has 4 GB. Ron wants credit use kept low, so run the whole suite very rarely: only when Ron asks, or before a release after large or wide-reaching changes, and say why first. After an ordinary change, run only the areas it touches (`node run.js "--only=..."`). Read only the failures and the last lines of the output, never the full PASS list. New behavior gets new checks in a named area; when wording changes, update the checks that read it.
